# What is deliberately not published, and why

This repository contains source code, notes and scripts only. The following is **left out on purpose**:

- **Firmware and tuning data**: wireless-charger IC firmware arrays (`nuvolta_1652`: `fw_update_nu1652.h`, `fw_update_nu1661.h`), UFS firmware images (`ufs_ffu`: only the code and the table of device models; the firmware blobs are not included and the build expects zero-filled placeholders), the platform-configuration header of `swinfo` (`config_platform_data.h`: a large table extracted from the stock module), gauge firmware and data-flash images of `bq27z561`, audio-amplifier and touch tuning data. To build such a module you have to generate those headers from your own stock module.
- **Keys**: no seal / unseal key value. `bq27z561` reads its gauge unseal key at probe time from the device-tree property `unseal_key` (4 bytes); the property name is in the source, no value is. The sources do contain the unseal / data-flash command sequences as code (MAC command numbers are public TI gauge commands), which is why the module carries a prominent warning in the README. **Correction of an earlier statement ("no 4-byte constant"): `ported/bq27z561/bq27z561.c` contains two 4-byte command data words with a sequential nibble pattern, one sent with the CO (charge-off) open/close MAC commands in `fg_set_co` and one with the clear-count-data command; they were already in the published commit 2253f2e, they are command parameters read from the stock code, not the seal / unseal key and not data-flash content, and they are kept because the code needs them. The owner may still decide to drop them (open decision in `PUSH_PLAN.md`).**
- **Stock binaries**: no `.ko`, no images, no disassembly dumps. Review reports quote short instruction excerpts and offsets of stock functions as evidence; they contain no binary data.
- **Personal and infrastructure data**: user names, e-mail addresses, build-server addresses, ssh key paths, local paths and were replaced by placeholders (`<user>`, `<build-server>`, `<ssh-key-file>`, `<work-dir>`, ...); third-party copyright lines of the original authors are untouched.
- **Other devices and projects**: nothing about other devices; mentions of another vendor kernel tree used as a template were neutralised.

Every file of the export was scanned twice with different pattern sets before it was proposed for publication (named private-data patterns, grep-style patterns, blob heuristics: hex runs, byte-array chains, base64-like runs, files over 5 MB, binary content, disassembly-looking lines, e-mail domains, seal / unseal key values); files that matched a blob or private-data rule were excluded. The reports added in the last round were checked the same way; the only e-mail addresses in the tree are the copyright and author lines of third-party headers.
