## 2. Findings, ranked by battery-safety / system impact

### HIGH

**QC6-1 (HIGH, robustness; active on an EU model with a PPS adapter) quickchg `mca_quick_charge_pps_ptf_work` cancels itself synchronously -> kworker deadlock.**
`mca_strategy_quickchg.c:3293-3310` (else branch `cancel_delayed_work_sync(&info->pps_ptf_work)` at :3308, XRING template code). Stock `.text+0x2634` (224 B): condition `(adp_type == PPS && mca_strategy_is_support_pps_100w()) || fake_pps_ptf` (ours: `&& is_eu_model`); when the PTF read returns 0 a static `check_num` (.bss+0xb0) counts to 5 then logs "this pps charger not support to get ptf, stop get action" and stops rescheduling; the else branch only clears `check_num` and returns. GKI `kernel/workqueue.c:3426-3458` (`start_flush_work` -> `insert_wq_barrier` behind the executing worker) + `__flush_work` `wait_for_completion`: flushing a work from inside itself never completes.
Scenario: EU model (`MCA_EVENT_IS_EU_MODEL`), PPS charger: `process_event` CHARGE_TYPE_CHANGE(11) (:3583) schedules the work every 10 s; on unplug DISCONNECT memsets proc_data (adp_type = 0) without cancelling it, or the adapter is re-detected as PD_VERIFY (12): the next run takes the else branch and blocks its system_wq worker forever (hung task); every later `cancel_delayed_work_sync(&pps_ptf_work)` (remove) hangs too. Fix: as stock (plain return, check_num limit, pps_100w condition).

**QC6-2 (HIGH in general, INACTIVE on dada) `mca_quick_charge_pre_charge_check` ignores the battery-OVP ban.**
`mca_strategy_quickchg.c:2132-2204`. Stock pre_charge_check is inlined in process_event (case 68, `.text+0x2dc8` +0x590..+0xb48): after the fg check it refuses to start when `proc_data.ban_cp_charging` (+0xa30; log "ovp_check:ban opening cp, exit quick charging", "dbcgx" variant under anti_overvoltage) or `try_en_cp_count >= 2` (+0xa34); both are set by `ovp_monitor_work` (:5683/:5690) when vbat exceeds the float voltage. Ours never reads them, so after the OVP monitor stops the CP for battery over-voltage the next CHARGE_ACTION restarts CP fast charging (OV -> stop -> restart loop). Dada: `anti-overvoltage-strategy = <0>` so ovp_monitor_work is never scheduled (:2098) -> inactive; any device/DT with the strategy enabled is exposed. Same function also lacks (stock +0x8e0..0xb48): `platform_class_cp_get_present(0)` ("cp not present, exit"), re-query of batt_auth/batt_missing (`mca_strategy_func_get_status(6,0x15)`, `(9,0x16)`) and the `batt_missing` test, re-read of adp_type when 0 (`protocol_class_get_adapter_type`, sets to_pd_verify), and the data_lock mutex around start_charging (missing imports mutex_lock/unlock, cp_get_present).

### MEDIUM

**QC6-3 (MEDIUM, active) reverse wireless charging does not stop wired quick charge.** Stock jump table (`.rodata+0`, index = event, 80 entries) handles **16** (MCA_EVENT_WIRELESS_USB_REVCHG, +0x2e0: log "wireless revchg event", `mca_vote(chg_disable_voter, "wireless_revchg", true, value)`) and has NO case 4; the only sender of 16 is `mca_wireless_revchg:mca_wireless_rev_charge_config` -> `mca_strategy_func_process(1, 16, v)`. Ours: `case MCA_EVENT_WIRELESS_REVCHG` (= 4) at `:3624`. Scenario: wired PPS charging + reverse wireless (TX) enabled: stock disables the CP path, ours keeps CP fast charging.

**QC6-4 (MEDIUM, active when the sender fires) three stock event cases missing** (stock cases 60/61/79, ours default):
60 HANDLE_ALLOW_CHARGE (+0x524: value 0 -> `mca_vote(chg_en_voter, "handle", true, 0)`, else false) sent by `mca_business_charger_comp:business_charger_process_handle_logic`; 79 DEBUG_CTRL_SOC_LIMIT (+0x6e4: `mca_vote(chg_disable_voter, "debug_soc_limit", true, value)`) sent by `strategy_buckchg_monitor_workfunc` when the debug SoC limit is reached (buckchg votes its own voters, then forwards to quickchg); 61 MASTER_BATT_CLOSE (+0x540: `base_close_curr = value*13/10`, `stop_charging = 1`, dual battery only). Scenario: the SoC limit / handle logic stops the buck but CP fast charging continues past the limit.

**QC6-5 (MEDIUM, active for PPS adapters that report PTF) PPS_PTF trigger value wrong.** Stock +0x4ac: `cmp pps_ptf, #2` -> "exit quick charge when PPS_PTF too high" + `chg_en "ptf" (true,0)`; any other value -> `(false,1)`. Ours `:3670` compares with `USBPD_QUICK_DPM_PORT_PPS_PTF_NOT_OVERTEMP` = 3 (`mca_quick_charger.h:189`; 2 is the BTF "WARNING"). At PTF warning the stock stops CP charging, ours keeps it; at 3 ours stops where the stock releases.

**BQ6-1 (MEDIUM, ACTIVE on dada, gauge WRITE) `fg_set_fastcharge_mode` enables the gauge fast-charge mode that the stock never enables on dada.** `bq27z561.c:1549-1586`. Stock `.text+0xfdb4`: if `support_new_soc_smooth` (+0x73c = 1852) -> `__mca_log_err "force set fastchg_mode disable"` (line 615), MAC write 0x3f (FASTCHARGE_DIS) with data 0, len 2, then `fast_mode = requested`; otherwise 0x3e/0x3f with **len 2 always** (no vendor test). Ours: `support_new_soc_smooth` is never parsed or tested anywhere in bq27z561.c, writes 0x3e on enable, and uses len 0 for MPC7021 (template). Dada DT `bq27z561_standlone@55` HAS `support_new_soc_smooth`. Scenario: every FFC start (quickchg start_charging / monitor `strategy_class_fg_set_fastcharge(1)`) puts the gauge into its FFC model, which the stock deliberately keeps off with the new SoC smoothing -> different gauge FULL/termination/SoC behaviour than stock.

### LOW-MEDIUM / LOW

- **QC6-6 (LOW-MEDIUM, mostly safe-side) DISCONNECT / CAP_CHANGE / CHARGE_ABNORMAL handlers** (`:3556-3560`, `:3586-3590`, `:3613-3615`): stock (+0x7c, +0x23c, +0x400) additionally sets `exit_cp_charging = 1`, releases the `pmic_temp_term` overrides on buck vterm/ICL that stop_charging installs (vterm = jeita + 30 mV, ICL 500) when `support_pmic_vterm_dynamics_adjust`, and on DISCONNECT cancels ovp_monitor/pps_ptf works, re-queues `delay_enable_pmic_work` with delay 0 (releases the `cp_chg_done` buck votes: on dada drop_fv_cycle = 0, so monitor's charge-done path always casts them), clears use_buck_chg_once_flag / clear_vstep_open_buckchg / cp_work_mode.last_stage, and takes data_lock in CAP_CHANGE. Dada: pmic-vterm flag absent -> the +30 mV override is inactive; the cp_chg_done votes stay up to 30 s after unplug (buck disabled, safe-side). - **QC6-7 (LOW, INACTIVE on dada: wired `hardware_cv = <1>`) hw-taper gate.** `mca_check_if_goto_hw_taper` `:269-324`: stock monitor_work +0x6c0..+0x750 jumps past the whole helper (no `taper_fcc_ma` store, no counter, no `taper_done_no_retry`) when `!hardware_cv && !(anti_overvoltage && cyclecount >= drop_fv_cycle)`; ours always stores `taper_fcc_ma` and runs the last-stage counter. - **QC6-8 (LOW) CHARGE_TYPE_CHANGE** (`:3564-3585`): stock sets `to_pd_verify = parallel_to_pd_verify = 1` for 12 (+0x220, `strh 0x101` at +0xa2a), so the next monitor runs `can_tbat_do_charge(info, 1)` (init branch, "PD VERIFY SUCCESS"); ours never sets it (only start_charging uses the init branch). pps_ptf_work scheduling: stock for 11 only if fake || pps_100w, ours if is_eu_model.
- **QC6-9 (LOW, inactive) IBAT_OCP** (`:3646-3657`): stock divides `proc_data.ocp_thr[]` (value 1 -> [1], 2 -> [0], 3 -> min) by 1000; ours uses the constants. Dada has no quickchg `ocp_threshold` -> defaults equal; sw_ocp_curr only used with base flip.

- **BQ6-3 (LOW)** fg_read_fcc: the `enable_fcc_default = 0` store has a different guard (facts 24/24, not resolved); fg_read_cyclecount ota path (known); fg_read_packvolt returns 3700 on fg_error where the stock returns an uninitialised w0 (no caller); fg_mac_write_block `len > 32` refusal (`:1371`) where the stock traps (safe-side) and the stock masks `len & 0xff` in `len + 2`.
