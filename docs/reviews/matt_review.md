# matt.ko - independent runtime-behaviour review (reconstructed source vs HyperOS 4.0 stock)

Reviewer: independent agent (did not write the code), 18.10.2026. READ-ONLY review: nothing in `work/re/src/matt` was edited, nothing built with Bazel, nothing flashed.

## 0. What was compared
- Source snapshot: `work/re/src/matt` (md5 list in `work/a17/review/matt_review_snapshot_md5.txt`; unchanged from start to end of the review).
- Stock: `<work-dir>` (md5 3bfdc1d311d8c0fdae08482cd3c7d931, vermagic 6.6.57).
- Ours: ThinLTO emulation of the current sources, rebuilt in my scratch `<work-dir>` with G1ad's `pb_ccl.sh` flags (`o/matt.lto.o`). Its fdiff output is identical to G1ad's own emulation (172/261 byte-identical, 89 differ). In addition every TU was compiled without LTO (`onl/*.o`, = the lto=none code shape) only to look for traps. No Kleaf/Bazel build was run.
- Running kernel for the kCFI checks: `<build-dir>` (6.6.144-android15-8-g309ffbbc5ec1, our kernel).
- Tools (new, in `work/a17/review/matt_tools/`, server copy `<work-dir>`; they import `compare_ko_v2.py`, run them from a directory that has it):
  - `rv.py` - per function: bytes+resolved relocations identical (IDENT) / same instruction sequence and a consistent register value pairing for every use (REGONLY = proven register-allocation-only) / else ORDER.
  - `sym.py` - layout/scheduling/regalloc-insensitive symbolic comparison: basic blocks, forward dataflow of symbolic expressions (stack slots folded, address sums flattened, commutative ops sorted, compare operands canonicalised), then the multiset of observable events (non-stack stores with address+value expression, calls with argument expressions, branch predicates, returns, traps, barriers, atomics, acquire loads) plus a branch POLARITY event (predicate + what runs when it is true). `COARSE=4` = depth-limited form, `WEAK=1` = weak successor signatures.
  - `calls.py` - per function multiset of call targets, indirect-call kCFI typeids, atomics, barriers, acquire loads, brk.
  - `kcfi_xm.py` - every indirect call through an `xm_*` kallsyms pointer: typeid at the call site (stock and ours) vs the typeid word in front of the target in our vmlinux.
  - `kcfi_cb.py` - preamble typeid of the module callbacks the kernel calls vs a kernel function of the same C type in our vmlinux.
  - `dd.py` - side-by-side compact disassembly with resolved relocations (used for all manual reading).
  - plus G1ad's `opb.py` (register-masked instruction multiset) and `compare_ko_v2.py` / `preamble_cmp.py`.

## 1. Findings

Severity: CRITICAL = crash / use-after-free / memory corruption reachable in normal use; HIGH = crash/corruption in a reachable but unusual case; MEDIUM = wrong protocol behaviour; LOW = harmless or practically unreachable; INFO = cosmetic (logs) or no runtime effect.
"Reachable" assumes MATT sockets exist, i.e. `/proc/sys/net/matt/enable`=1 (default 0, objects identical to stock). With enable=0 `matt_init_sock` fails and only init/exit and the failed-socket teardown run (those are identical to stock).

Inherited STOCK behaviour (identical in ours, i.e. not a reconstruction error, but a risk on the phone all the same):
- I1 `matt_sacktag_write_queue`: the SACK count comes from the packet (`ntohl(skb->data+0x30/0x14) >> 3`, clamped to 128) and up to 128 blocks (1 KB) are read from `skb->data+0x34/0x18` with no check against skb->len/headlen (only a 16-byte header check in `matt_rcv`) - remote out-of-bounds READ of up to ~1 KB per PACK/NACK (no write).
- I2 symbol table: `SYM_INET_UNREGISTER_PROTOSW` resolves "inet6_unregister_protosw" (stock copy-paste quirk): on unload the IPv4 protosw is unlinked under the IPv6 lock.
- I3 `matt_sendmsg_locked`: error paths return `copied` (0), never -errno.
- I4 code copied from the 6.6.57 kernel runs on our 6.6.144 kernel: `matt_skb_gro_receive` (no `skb_zcopy` check, no `SKBFL_SHARED_FRAG` propagation that 6.6.144 has), `matt_skb_attempt_defer_free`, `matt_gso_segment`; their struct offsets match 6.6.144 (byte comparison), their semantics are 6.6.57.
- I5 init failure with enable=0 -> `sk_common_release` -> `matt_destroy_sock` decrements sockets_allocated / inuse counters that were never incremented (statistics only, as stock).
- I6 `debug` sysctl default 0x1e: every trace of levels 1-4 is formatted and printed with pr_err on the data path.

Cross-cutting checks:
- Traps: per-function `brk` counts identical in stock and ours for all 261 functions (kCFI 0x82xx, BUG 0x800, array-bounds 0x5512) except F3; the non-LTO per-TU build has the same array-bounds traps plus F14.
- Lock/refcount/free/timer calls: per function, multisets of call targets, atomics (LSE and LL/SC), barriers are identical except F1 (`__matt_close`), inlining differences (inq_free, inputq/outq_init, ping_timer, bbr_init, init_module, sendmsg_locked's inlined matt_push) and extra trace call sites (rcv_data, adaptive_bit_unit_to_str). - kCFI, all three directions: (a) `preamble_cmp`: 244 functions, only F13 differs; (b) all 37 `xm_*` kallsyms pointers that are called indirectly: call-site typeid stock = ours = the typeid in front of the target in OUR 6.6.144 vmlinux (incl. the two G1ad fixes inet6_register_protosw 0x5f86e117 and skb_condense 0x50ad483a); the 41 table symbols all exist in our System.map, kprobes present; (c) callbacks the kernel calls: 44 checked against kernel functions of the same type (proto ops vs tcp_*, proto_ops vs inet_*, timers matt_timer_*_timeout = 0x91b4a83a like tcp_write_timer, tasklet, write_space, sk_destruct, skb destructor = tcp_wfree, encap_rcv/err = tcp_v4_do_rcv type, gso_segment = tcp4_gso_segment, udp-tunnel gro_receive 0x79422cd7 / gro_complete 0x2d71c532 = the typeids at the call sites in our vmlinux `udp_gro_receive` / `udp_gro_complete`) - all match.

- Struct offsets: every field offset used by the code is compared implicitly (identical bytes or identical store/load address expressions); chk_off.py covers 257 top-level non-bitfield members; NOT covered by it: 7 bitfields (matt_addr.udp_bind, matt_port.server, matt_rack reo_wnd_persist/dsack_seen/advanced, matt_pack delay_ack/loss_rate) and 11 nested members (matt_skb_cb tx union) - their accesses compare equal in the instruction/event comparison (e.g. rack.advanced `orr #0x40` at sk+0x1175 in both, cb tx fields at the same skb->cb offsets). Kernel struct offsets (sock, sk_buff, skb_shared_info, softnet_data) used by the code equal the stock's, so 6.6.144 == 6.6.57 for those fields.
- Receive engine invariants: every index into the 128-entry input SACK ring is masked `& 127`; sacktag writes at most 128 blocks and stores sack_used <= 128; make_pack/nack size the buffer from the same n they copy.

## 3. NOT verified / limits (do not read more into this review)
- `matt_rcv_data`, `matt_sacktag_write_queue`, `matt_sendmsg_locked`, `mibbr_main`, `matt_raw_skb_dump` are NOT proven equivalent. Checked for them: call/lock/atomic/trap multisets (equal), store target offsets (same set), trace arguments at every trace site (equal apart from F12 names), sack_remove loop, ack_update_rtt tail, bubble-sort bounds, the "fully" flag of clean_rtx_queue. Their remaining symbolic differences are register-cached vs reloaded values and block merging that my tool cannot normalise; a value-level inversion inside them could still hide there. `matt_clean_rtx_queue` was read more completely (only F3).
- The symbolic tool has no memory SSA (a load is the same value wherever it is), treats PHIs as unordered sets, and its polarity check is noisy for reordered condition chains; "SAME" means equal under these rules, not a formal proof. REGONLY pairs loop-carried values on first use.
- No Kleaf/Bazel build of the final .ko was made; the analysis is on the ThinLTO emulation (+ per-TU non-LTO objects for traps). Inlining in the real Kleaf build differs; semantics are the same source.
- Concurrency (BH vs process context, timer vs close races, RCU lifetimes) was not analysed beyond "same lock/atomic calls per function as stock"; lock ORDER inside a function was only compared where the function was read by hand.
- Interaction with the 6.6.144 kernel beyond kCFI/offsets/symbols (e.g. behavioural changes of kernel helpers between 6.6.57 and 6.6.144) not analysed except the copies listed in I4.
- No runtime test of any kind; BTF/bitfield layout only checked through code accesses; Xiaomi userspace contract (who sets net.matt.enable, which apps open IPPROTO_MATT=168 sockets) unknown.

## 4. Conclusion
matt is NOT safe to load as it is: F1 is a refcount underflow (use-after-free) on every close() of a MATT socket - a kernel crash / memory corruption the first time any app uses MATT with `net.matt.enable=1`. With enable=0 (default) the reachable code (init_module, cleanup_module, socket-creation failure path) is identical to stock, but "inert unless enabled" is not "safe": nothing stops a root/system process from enabling it, and I1 (remote OOB read, stock bug) is reachable as soon as MATT traffic exists.
Before a first test: (1) fix F1 (delete `sock_put(sk)` at the end of `__matt_close`) and re-run `calls.py` (expect no refcount/sk_free difference in any function); (2) fix F2 and F5 (one line each) and optionally F3/F4; (3) finish the open equivalence work on the five big functions in section 3 (or accept them as not proven); (4) first load only on a test phone with enable=0, check dmesg, unload (exercises I2), then enable on a throw-away test with one connection while capturing dmesg (KASAN kernel if available), never on the daily phone; (5) keep the "DO NOT LOAD" mark in STATUS.md until (1)-(3) are done.
