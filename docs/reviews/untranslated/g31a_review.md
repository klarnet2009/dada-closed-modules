## Метод
* Сырой `llvm-objdump -dr` (clang-r510928) обоих .ko: `<work-dir>` (6.4 MB), локальная копия в scratchpad сессии (`rvg31/`).
* `ann.py`: к каждому reloc ADD_ABS_LO12_NC дописывается полная C-строка из секции .ko (свой разбор ELF, без лифтера).
* `nd.py`: блочный alpha-diff одной функции (регистры переименовываются по первому появлению в блоке, цели ветвлений = L, reloc-цели = строка / RO / STATIC) **плюс проверка целей ветвлений** через карту выравнивания (`TARGET-MISMATCH/UNMAPPED`). Это только указатель: каждый ханк и каждая непокрытая цель прочитаны вручную в сыром листинге.
* `ro.py`/`dv.py`/`strs.py`/`lines2.py`: все не строковые ссылки в `.rodata*` и `.data*` по функциям с байтами, полные строки по функциям, множества `mov w2,#line` по функциям. `jtc.py`/`jt2c.py`: цели jump-таблиц сток→наша через карту выравнивания.
* Глобально по 4 модулям: полные строки логов по каждой функции совпадают (997/736/721/467 пар, diff пуст). Множества номеров строк логов совпадают во всех функциях (единственное «отличие» 20000 в process_irq = csel, см. п.4). VERIFIED.

## Прочее в тех же функциях (не из списка семи фиксов)
* **quickchg monitor_work, inline mca_check_if_goto_hw_taper: DIFFERS, только гонки (LOW, INFERRED по наблюдаемости).** Сток 0x1eb8 читает `cur_volt_para->volt_para_size` ДО `strategy_class_fg_get_fastcharge()` и использует это значение после вызова и для `last_cur_min` (с перечитанным указателем 0x938), и для `section == size-1` (0x1fec). Наша сборка читает size заново после вызова (0x62c) и ещё раз после `get_temperature` (0x750). В однопоточном случае одинаково, отличается только при смене `cur_volt_para` во время вызовов. Фикс (по желанию): `int size = vinfo->volt_para_size;` до вызова get_fastcharge, затем `proc->cur_volt_para[0]->volt_para[size-1].current_min` и `section == size - 1`.
* quickchg monitor_work check_charge_done: `count=6` у нас пишется после лога 2360, в стоке до него. Статик принадлежит функции, которую вызывает только monitor_work, поэтому разница не наблюдаема (CODEGEN). Это тот же класс «стор до лога», что фикс 3 G31a; при желании переставить для единообразия.
* Остальные ханки monitor_work (79) просмотрены: слоты стека, путь `info==NULL` (w26, мёртвый: `container_of` от work), -200/-500 через раскладку блоков (`<350` ≡ `>349`), шлюз hwid `0x496` через раскладку, хвостовые слияния логов. Новых различий нет, VERIFIED. regulation целиком я не перечитывал (G30e: 6 секций), INFERRED.
* wireless process_event: 910/931 равны, хвостовое слияние `queue_delayed_work_on` (125/2500) с той же целью возврата 0. VERIFIED.
