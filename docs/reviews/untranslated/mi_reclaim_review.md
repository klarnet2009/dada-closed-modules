## 4. Что делает модуль (умолчания enable=3, efficiency=3, stats=debug=0), режимы отказа
- При загрузке поток `umms_refill` (CPU = кластер самого слабого ядра) заполняет пул обнулённых order-0 страниц до totalram*0,4% (около 49 МБ при 12 ГБ, 64 МБ при 16 ГБ; INFERRED по формуле), учёт в NR_KERNEL_MISC_RECLAIMABLE. Дальше пул пополняется только при `refill_enable 1` (по умолчанию 0). Без MIUI-демона пул расходуется один раз.
- Пул: перед direct reclaim в `__alloc_pages_slowpath` (только order 0, только «важные» задачи: RT, QoS, умирающие, важные tgid, kthread, не фоновые по adj/prio) отдаётся страница из пула.
- skip_throttle: при file LRU >= 12800 страниц (50 МБ) обходит `throttle_direct_reclaim`, то есть почти всегда, и помечает задачу (бит0), чтобы её следующий shrink_slab был пропущен. shrink_slab пропускается и у важных задач в direct reclaim.
- tune_scan_type при MGLRU не работает: `LRU_GEN_ENABLED=y` и в стоке, и у нас, `get_scan_count` не вызывается (vmscan.c:6549/6820) (VERIFIED).
- Убийств процессов нет. Глобальный reclaim (до около 1 ГБ за запись) только по записи root в `event`.
- Баги стока, воспроизведены байт-в-байт (оставить ради эквивалентности): S1 exit без `tracepoint_synchronize_unregister()`: rmmod во время работы хука даёт UAF. S2 ошибка регистрации хука после старта потока оставляет пул неосвобождённым (утечка около 0,4% RAM). S3 пул записан как «reclaimable» без shrinker: MemAvailable/KReclaimable завышены на размер пула. S4 справка обещает «257 = 100MB+FILE», код берёт 256 МБ.
- Если бы наш код разошёлся со стоком в ветке: order>0 или неверная зона = порча памяти или страница не из той зоны для DMA; неверная маска cmpxchg = порча oem_data1[3]; неверный порог = лишний reclaim. Всё это закрыто побайтовой идентичностью 27 функций и чтением 3 оставшихся.
