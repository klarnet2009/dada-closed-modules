## 2. Findings, ranked by battery-safety / system impact

### CRITICAL

**BQ7-1 (CRITICAL, ACTIVE on dada at every fg update) `fg_get_batt_info` fills the ops struct in a layout the OS4 consumer does not use: the battery TEMPERATURE slot receives the cell VOLTAGE.**
`inc/bq27z561.h:733-743` declares `struct fg_batt_info {curr, volt, vcell_max, temp, rsoc, rm, fcc, cycle_count, soh}`; `bq27z561.c:1456` stores `data->temp` (built `fg_read_batt_info` +0x334 `str w8,[x19,#0xc]`) and `:1464` `fg_read_max_cell_volt(fg, &data->vcell_max)` stores the battery voltage in mV at +8 (built +0x4b4 `add x22,x19,#8` ... +0x580 `str w8,[x22]`; for non-MPC7021 gauges it is `fg_read_volt`).
Stock: the OS4 BTF of BOTH `bq27z561.ko` and `mca_strategy_fg_comp.ko` has `struct fg_batt_info {+0 curr, +4 volt, +8 temp, +12 original_temp, +16 rsoc, +20 rm, +24 fcc, +28 cycle_count, +32 soh}` (size 36); stock `fg_read_batt_info` (.text+0x15e4c) reads **32** bytes from reg 0x06 (`fg_read_block(bq,6,buf,0x20)` +0x108..+0x120; ours 16 bytes via `i2c_smbus_read_i2c_block_data`, the only import the stock does not have) and stores temp at +8 (+0x3b8), original_temp from reg 0x1e at +12 (+0x414), rm +20, fcc +24. Consumer: stock `fg_update_status` (fg_comp .text+0x558c) calls `platform_fg_ops_get_batt_info(0, &fg->batt_info /* +0xc84 */)` (+0x2e0) and then `ldr w21,[x19,#0xc8c]` (= batt_info+8, +0xb28) as the temperature for the extreme-cold compensation -> `batt_temperature`; our own fg_comp does the same (`mca_strategy_fg.c:2001`, `:2158`). Dada DT `strategy-fg { fg_type = <0> }` -> single-gauge path, i.e. this path.
Scenario: with our bq27z561 (and either fg_comp) the system battery temperature becomes ~3500..4500 (0.1 C) = 350..450 C at every update; JEITA (buckchg/quickchg can_tbat via `strategy_class_fg_ops_get_temperature` -> `fg->batt_temperature`) stops all charging, Android's overheat shutdown triggers, the real temperature is visible only as `original_temp`. Direction is "no charge" (no cell hazard), but every temperature-based protection then runs on a wrong signal. Fix: the stock struct order, a 32-byte read from 0x06, original_temp from 0x1e (`fg_convert_bytes_to_original_temp`), no vcell_max in this struct.

### HIGH

**BQ7-2 (HIGH, ACTIVE on dada at every probe, gauge DATA-FLASH WRITE not in the stock) `fg_set_term_config` writes MAC 0x456E (TERM_CURRENTS) with {0xDC,0x05}.**
`bq27z561.c:5073-5090`, called from `bq_fg_probe` `:5942`, BEFORE `fg_read_vendor` (`:5947`): `bq->fg_vendor` is still 0 (devm_kzalloc) = `BQ27Z561`, so the `fg_vendor != BQ27Z561` guard never skips and the write goes to every gauge (MPC8011B/MPC7012/NFG...). Built probe +0x460..+0x47c: `ldr w8,[x20,#0x3e0]; cbnz w8 -> skip; mov w8,#0x5dc; mov w1,#0x456e` -> fg_mac_write_block. Stock: `llvm-objdump -d` of the OS4 bq27z561.ko contains NO `#0x456e` at all (0 hits; ours 1); the stock probe's only gauge writes are the NFG1000 boot/OTA path gated by `support_nvt1000_ota` (+0x814, absent in the dada DT) and `fg_set_fastcharge_mode(bq,0)` (+0xe94). Scenario: each boot sends an unvetted DF write (TI address) to the dada gauge; if the gauge is unsealed (or the vendor's MAC accepts it) a termination/taper parameter of the pack is changed, i.e. FULL / termination behaviour of the gauge differs from stock and persists in the pack.

**QC7-1 (HIGH functional, ACTIVE on dada for every PPS / PD_VERIFY CP session; safe for the cell) `mca_quick_charge_open_path` votes the buck charge current to 0 and nothing ever releases it.**
`mca_strategy_quickchg.c:1419-1420`: `mca_vote(input_suspend_voter,"wire_qc",true,1)` and `mca_vote(buck_charge_curr_voter,"wire_qc",true,0)` (built +0x100: `mca_vote(ldr.x(a0+32),"wire_qc",1,0)`). Stock open_path (.text+0xa510) +0x108..+0x134: `x8 = adp_type==PPS ? +0x10 (buck_input_voter) : +0x8 (input_suspend_voter); mca_vote(x8,"wire_qc",true, adp_type==PPS ? 100 : 1)` (PPS: buck ICL 100 mA during the tune, not suspended), and at the end +0x384..+0x3c4 only for PPS with cp_enabled: `mca_vote(input_suspend,"wire_qc",true,1); mca_vote(buck_input,"wire_qc",false,0)`. All 13 stock "wire_qc" sites (stop_charging, enable_buck_charging, check_cp_work_mode, regulation x5, open_path x2, start_charging, qc_open_path) use input_suspend/buck_input only; `buck_charge_curr` (+0x20) never gets a "wire_qc" vote. Ours never releases it: stop_charging (`:676`) and the start_charging failure path (`:2083-2084`) release input_suspend/buck_input only. `buck_charge_curr` is a MIN votable (`mca_strategy_buckchg.c:3343`) whose callback calls `platform_class_buckchg_ops_set_ichg(effective)`. Scenario: first PPS/PD_VERIFY charge: CP runs (input suspended); when CP ends (taper/charge done "enable pmic for 30s", thermal exit, unplug/replug, or an open-path failure) the buck charger is left with FCC = 0 until reboot, also for later 5 V/QC adapters: the phone stops charging below 100 % / stops charging at all. Fix: as stock (PPS: buck_input 100 then release; others: input_suspend 1; no buck_charge_curr vote).

### MEDIUM

**BQ7-3 (MEDIUM, gauge WRITE via a 0664 sysfs node, active whenever userspace writes it) `fake_first_usage_date` writes the gauge; the stock only sets a flag.**
`bq27z561.c:5692` -> `fg_write_fake_first_usage_date` (`:2840-2874`): reads MAC 0x7B (UI_SOH block) and writes it back with data[11..13] taken from `tmp_buf[3..7]`, no length/digit check, no "already valid" check. Stock `fg_sysfs_store` (.text+0xf10, jump table `.rodata+0xf0`, id 36 -> +0x488): `strb (val != 0), [bq,#0x213] /* fake_usage_date */` and nothing else. Scenario: a HAL/user write of "1" makes ours read `tmp_buf[3..7]` past the `kzalloc(size+1)` (heap out-of-bounds read) and overwrite the pack's stored first-usage date (EU battery data) in the gauge DF with garbage. Also id 35 (`first_usage_date`, `:2876`): stock `fg_write_first_usage_date` (.text+0x9588) rejects anything but 8 digits ("Invalid date input", "input is not all digits") and always kfree's; ours has no validation (garbage date written when the stored date is 0/FF), refuses to overwrite a valid date (stock overwrites, with a 4x verify/"reset" loop) and leaks `tmp_buf` (also `fg_store_ui_soh` `:5136`, stock kfree +0x7ac).

**BQ7-4 (MEDIUM, conditional: MPC7012 gauges, i.e. manufacturer-name byte '7'; gauge WRITE loop) cutoff voltage read 0x4F but written 0x50.**
G13s fixed the getter only: `fg_get_cutoff_voltage` `:4222` reads 0x4F for MPC7012 (= stock .text+0x490c), but `fg_set_cutoff_voltage` `:4206` always writes 0x50. Stock `fg_set_one_cutoff_voltage` (.text+0x17274, fg_set_cutoff_voltage inlined, `__func__` string present) +0x4c..+0x68: `cmp fg_vendor,#4; mov w8,#0x4f; cinc w1,w8,ne` -> 0x4F for MPC7012. Ops slot `fg_ic_set_cutoff_voltage` -> fg_set_one_cutoff_voltage in both. Consumer: fg_comp `strategy_fg_update_vcuttoff_voltage` (called in every `fg_update_status`, `mca_strategy_fg.c:2393`) writes `vcutoff_fw` whenever the read value differs. Scenario: on an MPC7012 pack whenever vcutoff_fw changes (dod/cycle tables) ours writes the wrong MAC register (0x50) every fg cycle forever, because 0x4F never changes: repeated DF writes to an unrelated parameter. (Before G13s read and write both used 0x50: one wrong write, then stable.) The `value < 3000 && value > 3400` range test is dead in both (stock compiled it out too).

**QC7-2 (MEDIUM, conditional: dada units with the SY6541 second-source CP) open_path misses the 20 ms ADC settle.**
Stock open_path +0xa0..+0xd0: `if (cp_vendor == 5) { log "cp SY6541, wait 20ms for adc ready"; if (msleep_check(20)) return -1; }` before `platform_class_cp_get_battery_voltage`. Ours (`:1397-1417`) reads vbat right after enable_adc/set_mode. The dada CP node `sc8585_master@6e` is driven by `sc8581_sy6541.ko`, whose probe stores vendor 5 (`sc8581_probe` +0xadc `mov w8,#5; str w8,[x20,#0x104]`) for the SY6541 variant; `ops_cp_get_chip_vendor` returns that field. Scenario: SY6541 phone, first open_path: vbat not ready (0/stale) -> `cur_adp_volt = vbat*ratio + delta` far too low -> tune loop / open-path failure -> PMIC fallback, and with QC7-1 the buck then has FCC 0.
