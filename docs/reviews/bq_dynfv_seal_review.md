## A. `fg_set_one_dynamic_fv` (stock .text+0x1a5a0, 90 insns, ops slot +624 = 0x270)

### A1. Exact stock behaviour (VERIFIED, instruction level)
Struct offsets (stock BTF, G14g dump): +0x3e0 `fg_vendor`, +0x3ac `fast_mode` (bool, written only by `fg_set_fastcharge_mode` .text+0x108cc), +0x484 `ota_updating`, +0xe0 `i2c_rw_lock`, +0x10 i2c client, +0x151.. `regs[46]` (stock table: regs[18] ALT_MAC = 0x3e, regs[20] MAC_CHKSUM = 0x60).
1. `if (fg_vendor != 4 /* MPC7012 */) return 0;` (1a5c4..1a5cc) - no write, no log.
2. `cmd = fast_mode ? 0x3002 : 0x3003; delta = fast_mode ? -10 : -5;` (`csel`/`cinc` on `cmp fast_mode,#0`). BTF enum: 0x3002 = `FG_MAC_CMD_DYNAMIC_FV_FFC`, 0x3003 = `FG_MAC_CMD_DYNAMIC_FV_NORMAL`.
3. `u16 v = fv + delta` stored with `strh` (little endian: low byte first); no range check of `fv` or `v` of any kind (no compare on w1 in the function); truncation to 16 bits.
4. `ret = fg_mac_write_block(bq, cmd, &v, 2)` (.text+0xa69c). If `ret < 0`: `__mca_log_err("write dynamic_fv=%d failed, ret=%d", v, ret)` (line 7848) and `return ret`.
5. Read-back (only after a successful write): buffer cleared; if `ota_updating` -> read value 0 without bus access; else trylock loop on `i2c_rw_lock` (`usleep_range(40,50)`, TASK_UNINTERRUPTIBLE, no retry limit, leaves when `ota_updating` becomes set), `__fg_mac_read_block(bq, cmd, buf, 2)` (.text+0x1e28), unlock. Its return value is IGNORED; on any read error the value stays 0.
6. `__mca_log_info("ffc=%d, write=%d, read=%d", fast_mode, v, read)` (line 7855, `fast_mode` re-read for the log) and `return 0` - also when read != written. No compare, no retry, no error, no second write, no delay between write and read-back other than the transport's own.
Guards: ONLY the vendor check. No chip-id / device-name check, no seal-state check, no unseal (fg_set_seal is not called), no battery-voltage / current / temperature / charger-state check, no rate limit, no change detection.

Bus sequence (transport decoded, VERIFIED): `fg_mac_write_block`: returns 0 without writing if `ota_updating`; trylock loop on `i2c_rw_lock`; `secure_delay = cmd > 0x4000 || cmd == 0x1054 || cmd == 0x7b` (false for 0x3002/0x3003, so NO msleep(100)); i2c_transfer #1: reg 0x3e + `[cmd_lo, cmd_hi, v_lo, v_hi]` (one message, 5 bytes on the wire incl. the register byte); on error log "wirte block failed" and return; i2c_transfer #2: reg 0x60 + `[~(cmd_lo+cmd_hi+v_lo+v_hi) & 0xff, 6]` (MACDataSum, MACDataLen = len + 4); returns the result of #2; lock held for both. Read-back `__fg_mac_read_block`: write reg 0x3e `[cmd_lo, cmd_hi]`, `usleep_range(4000,4100)`, write-read reg 0x3e / 36 bytes, check echoed command bytes, length byte (35) and checksum byte (34), copy 2 bytes from offset 2.

### A2. Callers (VERIFIED in the stock modules)
`mca_buckchg_jeita_monitor_work` (+0xfc4): `if (info->support_dynamic_fv) strategy_class_fg_set_dynamic_fv(fv)` with the FV value the same pass votes to the "jeita" FV voter (compared against 4151 there; jeita_para FV columns are 4060..4580, so mV: INFERRED). Called on EVERY monitor pass while the flag is set (no change check); the return value is ignored. `support_dynamic_fv` = `of_find_property(node, "support-dynamic-fv") != NULL` (probe, two parse paths, info+0x1a4).
-> `strategy_class_fg_set_dynamic_fv` (class ops +0xe0; -1 if not registered) -> fg_comp `strategy_fg_ops_set_dynamic_fv`: -1 if `!fg_init_flag` (+2800), returns 0 WITHOUT writing if `cfg.fg_type == 1` (+1964), else `platform_fg_ops_set_dynamic_fv(0 /*master*/, fv)` -> role <= 1 and ops +0x270 non-NULL (else -95), kCFI-checked indirect call -> our slot 78.
Only `mca_buckchg_jeita` calls the class function; only `mca_strategy_fg_comp` calls the platform one (string / import scan of all vendor_dlkm modules).

### A3. dada global: the path is dead in the stock (VERIFIED from the static DT)
`support-dynamic-fv` occurs in none of the 8 vendor_boot DTs and not in the dtbo DT (the `mca_buckchg_jeita` node exists there, line 3388, without it). So on GLOBAL OS4.0.0.7 dada the stock jeita never calls the chain, and the stock gauge write never happens, whatever the gauge vendor is. Our stub (returns -EOPNOTSUPP) is therefore not observable on dada (the only caller ignores the result). Caveat: a bootloader-side DT fixup was not considered (INFERRED: unlikely). Which fg_vendor the dada gauge reports was NOT determined.

### A4. Data flash or RAM? Reversible? (UNVERIFIED, hints only)
Nothing in the binaries says what MPC7012 does with MAC 0x3002 / 0x3003. Hints that it is a run-time (volatile) parameter, all INFERRED: (a) below 0x4000, and the driver's own `secure_delay` list (the commands it treats as persistent writes: > 0x4000, 0x7b, 0x1054) excludes it; (b) no unseal before the write, while every stock data-flash writer (term-voltage update, cloud update, record-voltage, fl4p0) unseals first; (c) the design writes it on every jeita pass, which would be unusual for flash. Against: the MPC7012 command map is not public; the gauge is a pack-side device powered from the cell, so a phone reboot / power-off is NOT expected to reset it - even a RAM value would most likely stay until the next write or a gauge reset (INFERRED). Reversibility by power cycle: NOT established.

### A5. What one wrong byte would do (INFERRED)
Value byte order swapped (BE): e.g. 4475 mV = 0x117B would become 0x7B11 = 31505 -> an absurd FV parameter in the gauge; effect unknown (name suggests charge-full / termination / SOC scaling: wrong full detection or SOC is plausible). Command byte order swapped: MAC 0x0230 / 0x0330 = unknown commands on that gauge. Wrong delta: a few mV offset. 0x3002/0x3003 swapped: FFC vs normal parameter written to the other slot. Missing vendor guard: the same MAC to a TI / NVT / MPC8011B gauge with unknown meaning. Wrong checksum / length byte: on TI-family gauges the MAC write is not committed (unknown for MPC7012). The stock read-back offers no protection (logged only), so any of these would be silent except for the "ffc=, write=, read=" line.

### A6. Feasibility and recommendation
Feasible: 90 instructions, uses only transports already in our module (`fg_mac_write_block` = stock logic plus our extra `len > 32` refusal, irrelevant for len 2; `__fg_mac_read_block` present); a transcription of A1 can be proven with compare_ko / symcmp4 like the other functions. RECOMMENDATION: do NOT port for dada global; keep the stub. Reason: the stock path is dead on dada (A3), so porting adds an untested gauge-write path with unknown persistence semantics and zero behavioural gain. Port only if ALL hold: (1) a target DT sets `support-dynamic-fv` and fg_comp `fg_type != 1`; (2) the gauge reports MPC7012; (3) the MPC7012 meaning of 0x3002/0x3003 (RAM vs flash, units, use) is documented or observed on a STOCK device of that model (its own "ffc=, write=, read=" log lines); (4) the port is instruction-faithful to A1 (vendor guard, LE, len 2, deltas -10/-5, no unseal, read-back ignored, return 0) and passes symcmp4 with 0 only-stock / only-ours effects; (5) a separate independent review.

## B. `fg_set_seal` (stock .text+0x9918, 404 insns; ours 377)

### B1. The 3 guard differences (VERIFIED: symcmp4 `SKIPPHI=1 -v`, then by hand)
All three are the TI-only (fg_vendor == 0) unseal "step 5" write: after the four key-word writes and msleep(200), a 2-byte block `{0x2e, 0x00}` to reg 0x3e. The three facts: the `__fg_write_block(client, 0x3e, buf, 2)` call, its `< 0` result check (log "step 5 data flush failed," line 4980) and the `mutex_unlock(i2c_rw_lock)`. Stock-only guards on each: `ota_updating (chip+0x484, 1156) == 0` AND `mutex_trylock(&i2c_rw_lock /* +0xe0 */) succeeded` (loop with usleep_range(40,50); if ota_updating appears the write is SKIPPED and its result counts as 0). Ours: blocking `mutex_lock` and an unconditional write, because our `fg_write_block()` (bq27z561.c:397) lacks the stock gate. Same root cause, same guard pair, in `fg_set_force_report_full` (5 guard diffs) and `fg_set_verify_digest` (the sha256 challenge write), the other two users of `fg_write_block`. Practical effect in our module: none found - `ota_updating` is never assigned in our source (grep), so the stock gate would always pass; the difference is lock style only. Fix if wanted: give `fg_write_block` the stock form (ota check + trylock/usleep(40,50) loop), once, in the shared helper.

### B2. Other real differences (not counted as guards)
- Seal path (value == 0): the stock does `msleep(250)` after EVERY seal command (MAC 0x0030 word to reg 0x3e), before reading OperationStatus (MAC 0x54, 32 bytes, sealed = (byte1 & 3) == 3); ours reads immediately (bq27z561.c:3593-3597). Up to 3 attempts in both, `msleep(100)` between attempts in both. Effect (INFERRED): ours may see "not sealed" too early, resend the seal command sooner and give up after ~0.3 s of sleeps instead of ~1.05 s (3 x (250 + 100) ms); the commands written are the same. Fix: `msleep(250)` after the write (also after a failed write, as the stock).
- Our seal-path pre-check `if (seal_status == SEAL_STATE_SEALED)` reads a variable that is always 0 there: dead code, the stock has no pre-check; no effect.
- Return value: stock returns the last status-read result (0 on "already unsealed" / ota); ours returns an OR of results, but every caller in our module ignores it (the compiler dropped it). In the stock only the not-ported `fg_fw_clound_update` uses it.
- Log calls: same strings / lines, merged call sites in ours (codegen).

### B3. Writes compared (VERIFIED, key VALUES deliberately not reproduced)
Both binaries write exactly: unseal for vendors 1..4 (NFG1000A/B, MPC8011B, MPC7012): the two 16-bit key words from DT `unseal_key` (chip+0x20c, little-endian halfwords) to reg 0x3e, 300 ms after each; vendor 0 (TI): key word 2 (byte-swapped) twice 4 s apart, 5-5.1 ms, key word 1 (byte-swapped) twice, 200 ms, then `{0x2e,0x00}`; vendors >= 5: no write, log "unseal don't support"; up to 3 rounds, 100 ms apart, early exit on FA / UNSEALED. Seal: word 0x0030 up to 3x. Our function writes nothing the stock does not; the stock writes nothing ours does not, except that the stock SKIPS step 5 while ota_updating (unreachable in ours).
