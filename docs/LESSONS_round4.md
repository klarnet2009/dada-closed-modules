# Lessons from rounds 7 to 9 (charging reviews 4 and 5, hidden-behaviour audit, audio, TEE, Wi-Fi roaming)

Continuation of `docs/LESSONS_round3.md`. State of 19.10.2026 (night). Nothing was run on a device.

- **"Block order only" is a claim, not a result.** Many STATUS files of the charging family said that the remaining differing functions differ only in block order or register allocation. When a charge-pump boot-failure case that the stock falls through into the restore code was fixed in the buck-charging module, the diff of one function dropped from 34 lines to 9, which meant that the label had been hiding real behaviour. A systematic audit of every differing function of the family (`docs/reviews/charging_hidden_audit.md`) found three more hidden differences in buck charging (an override released on the wrong event, two overrides cleared on the wrong request), one in basic wireless (a buffer that the stock zeroes) and four in quick wireless (a flag that was never set, a comparison operator, a log level). The test that works: compare calls, stores and stack data **and the conditions under which each happens** (`tools/review4/symcmp4.py`); equal facts with an inverted branch are a difference.
- **A function that only differs in form can still be wrong in its neighbours' STATUS.** Several "differs only in the real build" and "registers only" statements of earlier STATUS files were wrong (`check_bypass_status` had an inverted early exit; `can_tbat_do_charge` had a missing store). The STATUS files keep both the claim and the correction.
- **Do not trust a case value that you did not decode.** Compare instructions of a lowered `switch` hold the pivots of a binary search. Three chip ids that were never case values were accepted by `aw882xx_dlkm` for rounds. Read the jump table or the dense compare chain; read the range check (`event - 2 <= 0x47`) to see which events the stock accepts at all (that is how a missing fuel-gauge OTA event was found). A kCFI hash proves the return type: `int (*)(void)` against `void (*)(void)` is a different hash and a trap on the first indirect call.
- **Emulate the stores when the order does not matter.** For an init function that writes dozens of fields per chip, the instruction multiset is useless and the diff is noise. A small emulator over `objdump` text (`tools/rounds/gx.py`) gave the final store state of the stock per chip id and compared it field by field with ours. It found real errors in the first run (a block written twice around a version read, an error message that does not exist in the stock, fields written through a pointer that the stock does not use).
- **Look for the helper that changes the return value.** In `tfa98xx_dlkm` a register-write helper printed "not init yet" and returned failure where the stock returns 0 silently. That one difference made a dozen callers look "too big" and was blamed on inlining for a round.
- **Signedness decides the code.** A signed index in a list bound, a loop counter that LLVM then fully unrolls, a `min` through `csel`, `smaddl` against `umaddl`: the stock was written with `int`, ours with unsigned or `goto` macros, and the result was both different code and, in `mi_game`, a different bound. Reading the multiplier instruction in the stock is cheaper than guessing.
- **Compile inference can be steered, but only by the source shape.** A variable declared at function level made a kernel with stack zero-initialisation emit an extra `memset` of a 500-byte buffer; the declaration inside the block removed it. A global that is not `static` stops LLVM from inferring a 0/1 range and gives `cbz` instead of `cmp #1`. An out-of-line copy used by one call site only is reproduced with a call-site attribute rather than `noinline` on the function. These are guesses about the stock source that the binary confirms, not knowledge of it.
- **A review is a snapshot.** Two modules were rewritten while an independent reviewer was reading them; the report names its snapshot (an md5 list) and says which findings belong to which version. Findings of review 4 were closed in a following round and re-checked by review 5, which found three new real problems in code that had just been "fixed" (a stage that was not re-selected after a temperature change, a gauge register table of the wrong length, a missing gauge-OTA event). Fixing is not finishing.
- **Reading a table index is not reading the hardware.** The 19 new accessors of `bq27z561` used the stock register indexes on the template register table and read the wrong register, and symbolic comparison called them equal because the struct offset matched. Compare the data a code path uses (here the 46-byte register table), not only the code.
- **Board identity can be a module parameter.** `platform_version` of the charging code is the `project` parameter of `hwid.ko`, set by the bootloader command line; the device tree does not hold it and its model string is shared with another phone. The table in `hwid.ko` maps project 2 to `dada`, which turns many "serious" differences (branches gated on platform versions 1, 3, 4, 5) into inactive code. This is read from the binaries and is to be verified on the device.
- **Firmware and data-flash code is not ported by default.** The fuel-gauge firmware-update, data-flash and term-voltage functions of `bq27z561` (25 functions) are deliberately not part of the port: a mistake there is not a wrong number in a log, it can brick a battery pack. They stay stock until a design with an independent review exists.
- **An investigation that finds nothing is a result.** A roaming complaint led to a full read of the roaming path, the defaults, the Xiaomi ini and the framework overlays. The conclusion was that the driver is not the cause: the Xiaomi thresholds make the phone hold an access point until -76 dBm, and the rest are hypotheses to test with logs. Writing that down, with what the code cannot tell, is better than a speculative fix.
- **Corrections of our own documentation.** Numbers of the form "function bytes N of M" from `compare_ko_v2` count differing functions; an earlier version of the status page listed them as identical for several modules. Check the direction of every number that is copied from a tool report into prose.
