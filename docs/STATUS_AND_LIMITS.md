## 2. The old tool has holes, the strict tool closes most of them

`tools/compare_ko.py` was the first equivalence check. It compares the bytes of each function, relocations, the names and sizes of global objects, exports and imports with CRCs and the modinfo strings. It does **not**:

- compare relocations of functions whose bytes differ;
- compare the **content** of objects (`.data`, `.rodata`, `.bss`, tables, `__param`, `__trace_printk_fmt`) or static variables, only name and size of globals;
- compare anonymous `.rodata` other than as a C string up to the first NUL;
- look at `__bug_table`, `__jump_table`, alternatives;
- look at the **kCFI type hash**, the 4-byte word that sits just before each function symbol. A wrong hash does not change a single byte inside the function, but the kernel traps at the first indirect call to it.
- look at the `depends=` line of the modinfo (depmod and modprobe use it);
- tell a real prototype from a forged one: when a stub provider exposes the stock CRC, a matching import CRC proves nothing about the prototype.

`tools/compare_ko_v2.py` checks all of the above except the last point (it reports forged-provider imports as INFO), plus the binding of every function, code that belongs to no function, and the kernel version magic by flags. Its self-test (`tools/review/v2_selftest.py`) injects 17 kinds of corruption and catches all of them. `tools/preamble_cmp.py` and `tools/verify_pkg.py` check the kCFI hashes against the stock module and against the hashes the kernel expects (read from `vmlinux`).

What happened when the strict tool was run over the 100 older EQUIVALENT claims: 8 were really different (data tables shorter than stock, wrong DAI names, default thresholds, `__param` permissions, kCFI preamble words). Seven were fixed, one (`minet`) is still PARTIAL: two functions carry an extra kCFI word that cannot be removed without changing the inlining. Before the fix, our own `binder_gki` build had passed the old tool (9 of 10 functions) and still carried a wrong kCFI hash in the probe that would have trapped on the first binder allocation.

Even the strict tool misses things. A later independent review of the Wi-Fi drivers (section 6) found that 14 of 21 objects, which had been filed as "relocation layout differences" for several rounds, really differed in content (a netfilter hook registered at the wrong place, wrong policy tables, a wrong default). And a string-text scan found one log message that differed while all function bytes were equal. What the strict tool still does not check: `.eh_frame` and `.BTF`; memory accesses without relocations; `__FILE__` in the bug table is compared by basename; trailing zeros of anonymous pieces are ignored. Metadata always differs and is accepted: `intree=Y`, `scmversion=`, `srcversion=`, `staging=Y` versus `built_with=DDK`, the LTO `.note.Linux`, and `depends=` where a build named stub providers.

## 3. What a multiset diff proves, and what it does not

For modules that are not byte-identical (every PARTIAL module and the charging reviews) we compared, per function, the **multiset of instructions with registers masked**: stack accesses, frame setup, register moves, unconditional jumps and `ret` are dropped; `ldp`/`stp` are split; comparisons are normalised. Functions of the same module that were inlined in one build and not in the other are expanded before comparing. The result per function is one of LAYOUT (multisets equal), INLINE (equal after expansion), SELECT (only ALU/branch instructions differ), CONST (immediates differ too) and REAL (loads, stores, calls or traps differ). See `docs/reviews/multiset_audit.md` (the package and 31 PARTIAL modules) and `docs/reviews/multiset_audit2.md` (second part, with the bugs it found, and a third part: a search for globals that the stock reads where ours has a constant); both are English translations of the original working reports.

It proves, when the multisets are equal: the function performs the same memory accesses (opcode, width, offset), calls the same functions the same number of times, contains the same constants and the same trap instructions (`brk`, from `BUG_ON`, fortify, bounds checks). That is what found a self-deadlock (`getsockopt` took a lock twice), wrong kCFI prototypes that would trap on the first call, a missing SACK loop that the sanitizer had replaced by `brk`, and several fields read from the wrong source (for example `p->on_rq` instead of `p->se.on_rq` in `mi_game`, an unzeroed array in `mi_low_lat_mem`).

It does **not** prove equivalence: operations may be permuted; an inverted branch with a mirrored layout has the same multiset; data values in `.data`/`.rodata` are not looked at (that is `compare_ko_v2`); the class REAL is a heuristic and does not prove a bug. Control flow was analysed only for the functions the audit lists. The package audit (all modules built from our sources, 1758 functions) found no difference apart from two layout cases and two functions in another section.

It does not make the family safe: no hardware test exists, control flow was compared symbolically for the differing functions only, and the newer modules (`mca_smart_charge` ... `mca_strategy_quickchg`) were **not** part of it.
- Review 4 (the four wireless/buck/smart-charge modules after their first rewrite) found real differences, all of them fixed in the next round: **quick wireless `stop_charging` called the PMIC enable directly where the stock votes `"quickchg"` into the charge-enable voter** (the PMIC could be switched on again against a JEITA, over-voltage or battery-missing stop; HIGH); the buck-charging monitor lacked the stock reaction to a missing charge pump (forced 5 V); quick wireless never read `max_rx_vout_request` (19500 mV in the device tree), so it asked the receiver for 0 mV; a wrong start current for the charge pump (700 mA instead of 500); an inverted early exit in the smart-charge bypass debounce (the old STATUS said "registers only", which was wrong); a condition built with if/else-if instead of OR in the 30 W authentication limit (one rare adapter case lost its thermal limit); the template interrupt handler of basic wireless (no 850 mA limit for a weak 15 W EPP transmitter, a TX voltage range that ignored the platform version, no thermal notification); `get_status` that never returned INIT_OK.
- Review 5 (the rewritten code of review 4's modules plus `mca_strategy_quickchg` and `bq27z561`) found the buck-charging and basic-wireless code close to the stock but **real differences in three modules**: quick wireless did not re-select the charging stage after a battery-temperature zone change (HIGH: on the device-tree tables a cooling battery would have read one entry past the end of a 4-row table and used heap memory as the CV threshold; fixed by setting and consuming the stock `zone_changed` flag); it ignored the fuel-gauge OTA event (stock stops quick wireless charging during a gauge update; fixed); in `bq27z561` all 19 new register accessors used the stock register indexes on the template register table, i.e. every one read the wrong gauge register (fixed by taking the stock 46-byte table), and the core readers accepted a voltage up to 10000 mV where the stock rejects above 5000 mV (fixed, thresholds from the stock constants); `mca_strategy_quickchg` regulation and monitor were still the older template with the restored stock functions unreachable (these were then rewritten). One review claim was wrong and is documented: the 4:1 to 2:1 transition that review 5 expected does not exist in the stock.
- **Hidden-behaviour audit** (`docs/reviews/charging_hidden_audit.md`): earlier STATUS files called many remaining differences "block order only". Every differing function of the family was re-compared on the real stock `.ko` with a symbolic tool (`tools/review4/symcmp4.py`) that checks calls, memory stores, stack data **and the conditions guarding each of them**, so that equal facts with an inverted branch no longer pass. Result: for most functions the label was right, but **"block order only" had hidden real behaviour in the buck-charging module**: a charge-pump boot failure event that must fall through into the charge-restore code only voted in ours (found in the previous round after the first diff shrank from 34 to 9 lines once the fallthrough was added), a `master_batt_missing` input-current override that was released also on a "battery missing" event (the stock releases it only when the battery comes back), two `pmic_temp_term` overrides cleared on a disable request, and in quick wireless the `zone_changed` flag of review 5. All were fixed and the functions became byte-identical. The audit also lists, ranked by battery impact, what is **still open**: the quick-charge shutdown after a hardware action (the stock turns both charge pumps off and drops the adapter to 5 V; ours did neither at the time of the audit and was rewritten from the stock disassembly in the following round), stale override flags in the quick-charge voter callbacks (safe side), the `bq27z561` accessors without range checks (fixed in the following round) and the base-flip-only differences.
- **`platform_version` is not a property of the device tree.** It is the `project` module parameter of `hwid.ko` (set by the bootloader command line) and `hwid.ko`'s product table maps project 2 to `dada` (1 haotian, 3 miro, 4 xuanyuan, 5 bixi, ...). The consequence for the code: branches gated on `platform_version` 1, 3, 4 or 5 (the 20 V TX range of basic wireless, the 4:1 bridge switching, the buck-charging term-current votable, one `update_aicl_cfg` gate) should not run on a dada, and several differences that look serious are therefore inactive. **This is read from the binaries only and is to be verified on the device**; the device tree cannot confirm it (its model string is shared with haotian).

**Enum-name audit** (`docs/reviews/charging_enum_audit.md`): the shared stub headers carried enumerator names and values that differ from the stock BTF (178 mismatching enumerators over all stub trees, mostly `charge_dfx_ele` and `mca_event_ele`). The BTF enums of all 104 stock charging modules were dumped and compared with every stub tree and every finished charging module. Result: no finished module passes a wrong number (the immediates in the `.ko` equal the stock ones); wrong *names* (right value, name of another enumerator, i.e. a misleading source) were found in `mca_business_charger_comp` and `mca_strategy_fg_comp` and fixed, with an identical rebuilt binary; a few harmless alias names remain in other modules and are listed in the report. The old shared stub headers carry a warning comment.

- **Reviews 6 and 7** (quick-charge, quick wireless, `bq27z561`): review 6 found `mca_strategy_quickchg` `process_event`, `pre_charge_check` and `pps_ptf_work` not equal to the stock and one active gauge-write difference in `bq27z561` (fast-charge mode); review 7 found, in the snapshot of the `bq27z561` rewrite, a CRITICAL defect (the battery temperature slot of the info struct received the cell voltage, about 400 C) and a HIGH one (a data-flash write at every probe, which the stock does not do). Both were fixed afterwards (`bq27z561/STATUS.md`). Later reviews of the battery-emergency chain, of the `bq27z561` probe and of the dynamic-FV / seal helpers listed more differences (several in code that is dead on a `dada` because its device tree lacks the property); most were fixed in later rounds.

What is **not** covered by an independent review at the time of this update: the code written after the G22 review is partly covered (the seven quick-charge / basic-wireless fixes of the afternoon were independently re-read; the fixes applied afterwards, the results of the all-function audits of the charging family and `bq27z561`, the fuel-gauge compensation functions and the audio drivers were not), and the `regulation` and `process_event` bodies of quick-charge, which no tool and no reader has proven equal to the stock as a whole. The `bq27z561` data-flash path is gated like the stock but was never executed. The audits of the final round are classifications by a reader or tool of every differing function (`CODEGEN` / fixed / unproven); where a body is marked unproven it stays so in the module `STATUS.md`.

Reviews are static reading of disassembly against C. They do not replace running the code.

## 6. Wi-Fi (`qca_cld3_*`)

See `docs/WIFI.md`. Short version: five variants (`peach`, `peach_v2`, `kiwi_v2`, `qca6750`, `wcn7750`) of the public Qualcomm/OnePlus `qcacld-3.0` tree plus our Xiaomi extension code; all five PARTIAL; no function of any variant is missing or extra; 17826 of 18446 functions of `peach_v2` are byte-identical (18314 with a `#line` pin table that only equalises line numbers; both numbers were measured again on 20.10.2026; the other variants: `kiwi_v2` 17657 of 18271 and 18138 pinned, `peach` 17425 of 18324 and 17904, `qca6750` 15309 of 15880 and 15763, `wcn7750` 17369 of 17981 and 17853); a data-table audit of `peach_v2` (`docs/reviews/wifi_tables_audit.md`) compared all 2828 named data objects by content and found 8 differing names, and one proven behaviour difference (in `dp_rx_cksum_offload`) was fixed. An independent review (`docs/reviews/wifi_review1.md`) found 11 findings (F1-F11); F1-F7 were fixed in the next round (F1: the P2P header-compression netfilter hook was registered at the wrong hook point, which would have dropped every compressed packet of a Xiaomi peer). After that round the remaining differences were examined function by function and no further functional difference was found at the level of binary comparison. That is a statement about what binary checking can see, not a statement that the driver works. Rounds 10 and 11 found a few more real differences (for example a log string that differed while all function bytes were equal, found only by scanning relocated strings) and then ran out of them. A separate read-only investigation of a roaming complaint (`docs/reviews/wifi_roaming_investigation.md`) found **no roaming bug in the driver code**: roaming is done by the Wi-Fi firmware and the host only passes thresholds, which come from the Xiaomi `WCNSS_qcom_cfg.ini` (details in `docs/WIFI.md`).

## 7. Known bugs of the **stock** modules

Found while reviewing the reconstructions. They exist in the stock binaries and are reproduced on purpose in our sources (identical behaviour was the goal), **except `matt` S1/S2, where our source contains two deliberate hardenings** recorded in the module `STATUS.md`. Please do not copy them into anything that handles untrusted input.

`matt` (disabled by default, `net.matt.enable=0`):

- **S1 (remote)**: `matt_sacktag_write_queue` reads up to 128 SACK blocks (1 KB) from the packet without checking the length of the skb: remote out-of-bounds read.
- **S2 (remote)**: `matt_rcv_data`, when an out-of-order skb overlaps a queued one, frees it and then continues into the acknowledgement part, which reads one byte of the header from the freed data: remote one-byte use-after-free read.
- S3: on unload the IPv4 protocol switch entry is removed with `inet6_unregister_protosw`.
- S4: if the work queue cannot be created, `init_module` returns 0 and the module stays loaded half initialised (out of memory only).
- S5: with `enable=0`, socket creation fails and the destroy path runs on a socket whose timers and queues were never initialised; this is safe only because the kernel zeroes allocations (`init_on_alloc`; check `/proc/cmdline` has no `init_on_alloc=0`).
- S6: a store before a NULL check in `matt_transmit_skb` (unreachable, both callers pass a valid pointer).

`qca_cld3_*` (found by `docs/reviews/wifi_review1.md`):

- the P2P header-compression code (`dlhc_remember`, `__rx_inet_hook`) accepts remote input from any P2P peer without proper length checks (out-of-bounds read, a possible BUG on a non-linear skb) and ignores its enable sysctl;
- the Xiaomi fast-ACS path in `wlan_hdd_cfg80211_do_acs` fills fixed 101-entry arrays from a user-supplied list: an out-of-range count traps (kernel panic from a vendor command that needs CAP_NET_ADMIN) or overruns a heap buffer.

Because the F1 fix restores the stock hook point, these remote parsers are reachable again exactly as in the stock driver.

`mitee_dlkm` (found by `docs/reviews/mitee_review1.md`, 16 items; all are reproduced on purpose):

- unload and unbind are unsafe: `remove` does not stop the receive thread, does not drop the resource-manager notifier and frees the buffers it may still use; `tui_exit` leaves the device classes behind and unregisters the region before `cdev_del`. **Never `rmmod` it.**
- TEE-triggered: a `FREE_SECMEM` request with an unknown handle is not checked for "not found" and goes into `hyp_assign_table`/`kfree` on a non-object; `GET_FONT_BUFFER` does not compare the requested size or offset with the font size; `secmem_lend` returns success without writing the handle when the list entry allocation fails; a failed `hyp_assign_table` in `shm_register` is only logged and sharing continues; unknown handles in `shm_unregister` pass a NULL scatter table.
- the request/reply path waits without a timeout, so a secure VM that stops answering hangs the caller; `gh_msgq_register` is not checked with `IS_ERR` and the probe leaks its buffers on every error return.
- user-triggered: `tui_shm_create_fd` returns with its mutex held on the invalid-name path, and copies a user-supplied 16-byte name without a terminating NUL; the anonymous fd keeps a raw pointer to the shared memory without a reference; the `mem` branch of `SHM_ALLOC` allocates user-sized, non-zeroed `vmalloc` memory that is mapped back to the caller; `tee_shm_register` takes an `int` page count from a user length without a cap.
- `/proc/mitee_log_key` is created with mode 0444 and `key_read` ignores `size` and `*ppos`, always copying 345 bytes (on the stock ROM only SELinux protects the key).

Also: the exported charging-family sources carry some stock quirks on purpose, for example a checksum in `mca_smart_charge` that sums `total_len` bytes without a bound check, and a copy without NUL in `mca_basic_wireless` debug code; in `mca_strategy_quickchg` the stock calls `get_vstep` twice and throws the first result away, and dereferences the hwid pointer early without a NULL check; in `mca_strategy_buckchg` (`wls_revchg_monitor`) a hit of the voltage range on the sixth re-read still ends in "request 9V vbus fail".

## 8. Forged CRCs, stub providers

Some modules were only made to compare equal by forging export or import CRCs, by building against stub provider modules, or by `#line` pins. Where and how: `docs/HACKS_AND_FORGED_CRCS.md`. A forged CRC changes only a number in `__versions`/`__kcrctab`; if the real prototype or struct differs from the forged one, the module would still load but the ABI would not match.

## 9. Kernel drift: 6.6.57 versus 6.6.144

The stock modules were built against kernel 6.6.57 headers, ours are built against 6.6.144 (the kernel of the package). Some differences in function bytes, bug-table line numbers and export CRCs are therefore not errors in our source: `readl()`/`writel()` call `log_*_mmio` unconditionally in 6.6.57, `netif_tx_stop_queue()` writes `trans_start` and a barrier in 6.6.144, `poll_wait()` has an extra barrier, an earlier version of this page said that `task_struct.mm` moved; the BTF audit of 20.10.2026 showed this is wrong (`mm` is at +0x5a0 and `active_mm` at +0x5a8 in both kernels: the one place that differed was a real source error in `mitee_dlkm`, fixed), `cfg80211.h`/`skbuff.h`/`netlink.h` line numbers moved (151 of the 155 Wi-Fi functions with differing bug-table lines are header vintage). The Wi-Fi build therefore force-includes `ported/qca_cld3_xiaomi_ext/xm_compat_6657.h`, which restores the 6.6.57 bodies of `netif_tx_stop_queue`, `readl` and `writel`. **That header is a build-environment emulation, not Xiaomi code.** It also disables a macro-redefinition warning for every translation unit. Several forged CRCs have the same cause (a struct of the other tree).

## 10. Not covered at all

- Behaviour on hardware. Not one module was loaded; not even a test load under `dmesg` was done for the modules that reviews call ready for one (`lb`, `cameramsger`).
- The charging chain as a whole: the modules were compared one by one against the stock; the protocols between them are as in the stock only as far as the individual calls match.
- Concurrency and races (the reviews looked at lock and reference balance, not at schedules).
- Differences between the headers and structs of the two kernels beyond those that show up as differing bytes. A struct-layout audit (`docs/reviews/struct_layout_audit.md`: BTF of both kernels, 102978 `current->` accesses of 534 modules, imports of 636 modules) found no field that a stock module accesses shifted; it does not cover 421 platform modules whose BTF is built on a vmlinux that was not available, accesses that do not go through `current`, or any function behaviour.
- Device tree, firmware and userspace parts.
